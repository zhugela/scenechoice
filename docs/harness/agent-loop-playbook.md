# Agent Loop 操作手册（负责人本人拍板版）

> 生效日期：2026-11-20
> 来源：负责人 11-20 会话口述回答。这份比 `AGENTS.md` 的一般规则更具体，冲突时以本文件为准。
> 维护者：Hermes。任何一条改动都要负责人本人点头。

## 一、负责人的四个答案 → 落成的规则

| 问题 | 负责人的回答 | 落成规则 |
|---|---|---|
| 怎么判断"做完了" | 早上起来检查前后端功能有没有实现、是否符合原计划；两个方案时看是否符合产品需求；**不看代码、也不看 diff** | **R1** 判断标准 = 用户可见行为与产品需求，不是代码质量 |
| | | **R2** 因为不看代码，所以每轮必须产出**可观察证据**（能调的端点 / 测试名 + 数字）。没有可观察证据 = 我证明不了 = 不算做完 |
| 怎么找信息 | 不认识的 API 让 AI 查；Hermes 的定位是查知识库（认可） | **R3** 我优先查 MyBrain / 本仓文档，查不到才联网；结论必须带文件路径或 URL |
| 怎么检查工作 | 不读 diff；AI 写完自己也不自查；**自查清单必要**；数据层与业务层一样严格 | **R4** 每轮交付必附《自查清单》（见第五节），他照着核，不需要读 diff |
| | | **R5** 数据层（迁移 / 事务）不降低标准，反而要加变异测试 |
| 什么时候帮忙 | 卡住才问，不要每步都问；读代码时**他先讲、我挑错**；**commit 由我做**；长期有 super agent 帮 review | **R6** 默认自主推进，只在四类情况停下问他（见第四节） |
| | | **R7** 讲代码 = 负责人先脱稿讲，我只挑错、不给答案 |
| | | **R8** commit 由 Hermes 执行；他只看报告 + 自查清单 |
| | | **R9** Codex / super agent 是外部审查方，Hermes 负责回灌修复与独立复验，不采信任何 agent 自述 |

## 二、每轮固定 9 步

| 步 | 谁 | 动作 | 停手条件 |
|---|---|---|---|
| 0 | Hermes | 取基线：`git status` + 全量 `pytest -q` | 基线红 → 先修环境，不开新活 |
| 1 | Hermes | 写任务书 `PLAN.md`：输入 / 输出 / 边界 / 验收标准 / 禁改清单 | 负责人一句"按这个做" |
| 2 | Claude Code | 只实现**一个**功能点 | 超出任务书范围 → 打回 |
| 3 | Hermes | 轻门验证：全量 pytest + diff 复核 + 一条反例/变异 | 数字没往前走 → 打回 |
| 4 | Codex / super agent | 只审 diff，出「阻塞 / 建议 / 可忽略」三级清单 | 有阻塞级 → 进第 5 步 |
| 5 | Claude Code | 只修阻塞级，**禁止靠改测试预期变绿** | 动了测试预期 → 打回 |
| 6 | Hermes | 复验：全量数字 + 禁改文件比对 + 变异测试 | 不达 → 回第 5 步 |
| 7 | Hermes | 负责人**读懂门**：他脱稿讲，我挑错（R7） | 讲不清 → 不给进下一步 |
| 8 | Hermes | 落盘 `progress.md` + `feature_list.json`，evidence 只写真跑出来的数字 | — |
| 9 | Hermes | commit（R8）；push / 合 master 才问他 | — |

> 第 4 步的轻重可以调：数据层/迁移/权限走全量审查；业务层可攒 3~4 个功能点再审一次，省时间省钱。

## 三、四个角色的边界

| 角色 | 做 | 不做 |
|---|---|---|
| Hermes | 需求分析、任务书、独立复验、变异测试、落盘状态、commit、挑错 | 不写完整功能代码；不替他 review；不采信 agent 自述 |
| Claude Code | 按任务书实现单个功能点 | 不改测试预期；不动禁改清单；不自行扩大范围 |
| Codex / super agent | 只审 diff 的外部视角 | 结论可能含幻觉，必须人过滤（历史上有过约 1/4 误报） |
| 负责人 | 判断是否符合产品需求、读懂门、决定合不合 | 不读 diff（R4 用自查清单代替） |

## 四、必须停下问负责人的四类情况

1. **要花钱**的调用（真实 DeepSeek 评测、批量 token）
2. **不可逆操作**（删库、改已发布迁移、rewrite 历史、push 到 master）
3. **方案冲突**（产品需求与现有实现矛盾，或两套方案各有代价）
4. **禁改清单越界**（必须改的时候先说清为什么）

其他情况：自主推进，做完一次性汇报。

## 五、自查清单模板（交付时每条都填数字）

- [ ] 一句话说清：用户在哪儿操作、操作后看到什么变化
- [ ] 有没有可调用的 HTTP 端点？没有 → 为什么这轮不该有
- [ ] 正常路径证据：测试名 + 结果
- [ ] 失败路径证据：至少 1 条，写明触发条件
- [ ] 全量测试数字：改前 `___` → 改后 `___`
- [ ] 有没有改动禁改清单里的文件
- [ ] 有没有改动任何已有测试的预期结果
- [ ] 有没有改依赖（`requirements.txt`）
- [ ] `progress.md` / `feature_list.json` 是否已更新
- [ ] 变异测试：把关键判断故意改坏，测试会不会变红（数据层必做）

## 六、负责人的自学契约

- 代码由 AI 写、负责人**不读 diff** → 唯一的护栏是**读懂门**（第 7 步）。
- 读懂门形式：Hermes 出 3 个针对本轮代码的问题 → 负责人脱稿口述 → Hermes 只挑错、不给答案 → 卡壳回到源码重读。
- 说不清的功能不进下一步。**"代码存在" ≠ "负责人掌握"**。
