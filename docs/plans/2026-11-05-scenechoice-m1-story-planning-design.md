# SceneChoice M1：故事规划 PoC 设计

> 状态：设计基线｜日期：2026-11-05｜前置条件：M0 测试通过

## 1. 目标与阶段门

M1 只验证一件最危险的事：DeepSeek 能否把用户的一句话灵感稳定转换为一份可执行、可完结的互动短剧蓝图。

阶段门：使用 20 个不同题材的固定样例进行评测，至少 16 个蓝图同时满足结构校验和业务规则校验，才进入数据存储、完整互动引擎和前端开发。

M1 不接数据库、Vue 前端、RAG、LangGraph 或多智能体。

## 2. 已确认的产品决策

- 创建故事时一次生成完整的 3 集或 5 集蓝图；
- 正文在玩家进入具体一集时再生成；
- 每集固定提供两个选择；
- 两个核心状态由 AI 根据故事动态命名；
- 所有核心状态统一使用 0～100 的整数范围；
- 至少提供三种可达结局；
- 规则决定事实和后果，AI 负责叙述；
- 模型输出只有通过后端校验后才能成为有效蓝图。

## 3. 方案比较与选择

### 方案 A：完整蓝图优先（采用）

先确定角色、每集冲突、反转和结局条件，再逐集生成正文。优点是能保证收束、控制成本并提前发现不可达结局；代价是玩家的自由输入能力较弱。

### 方案 B：边玩边规划（不采用）

每次选择后再临时生成下一集。自由度高，但更容易漂移、烂尾，无法证明“保证完结”的差异化承诺。

### 方案 C：预生成所有分支正文（不采用）

能获得稳定体验，但分支数量指数增长，生成成本和无效内容过高，不适合 MVP。

## 4. 领域 Schema

### StoryBlueprint

- `title`：短剧标题；
- `logline`：一句话简介；
- `genre`：题材；
- `theme`：主题；
- `episode_count`：只允许 3 或 5；
- `characters`：2～4 个主要角色；
- `metrics`：恰好两个核心状态；
- `episodes`：数量必须等于 `episode_count`；
- `endings`：至少三个结局及其触发条件。

### CharacterBlueprint

- `id`：蓝图内稳定、唯一的英文标识；
- `name`：展示名称；
- `role`：在故事中的身份；
- `goal`：公开目标；
- `secret`：推动冲突的秘密；
- `personality`：一到三个核心性格标签。

### MetricBlueprint

- `id`：蓝图内稳定、唯一的英文标识；
- `name`：与故事相关的展示名称，例如“观众信任”；
- `description`：状态代表的故事含义；
- `initial_value`：0～100；
- `low_label` / `high_label`：低值和高值的语义。

### EpisodeBlueprint

- `number`：从 1 连续递增；
- `objective`：本集叙事目标；
- `conflict`：核心冲突；
- `required_events`：必须发生的一到三个事件；
- `cliffhanger`：非终集悬念；
- `choices`：恰好两个选择方向；

最后一集不再制造未解决的新主线，必须负责回收冲突并进入结局。

### ChoiceBlueprint

- `id`：蓝图内唯一标识；
- `text`：面向玩家的选择文案；
- `intent`：该选择代表的行为意图；
- `effects`：对一个或两个核心状态的预计变化；
- `consequence_hint`：给后续正文生成器的后果提示，不直接向玩家泄露完整结果。

### EndingBlueprint

- `id`：唯一标识；
- `title`：结局标题；
- `summary`：结局含义；
- `conditions`：基于两个状态的可计算条件；
- `priority`：多个条件同时命中时的确定性优先级。

## 5. 数据流与职责边界

```text
CreateStoryRequest
  → PromptBuilder
  → DeepSeekClient
  → JSON
  → Pydantic Schema 校验
  → BlueprintValidator 业务规则校验
  → 合格 StoryBlueprint / 明确失败
```

- `PromptBuilder` 只负责把产品约束转换成模型指令；
- `DeepSeekClient` 只负责网络请求、超时和模型错误转换；
- Pydantic 负责类型、数量、枚举和数值范围；
- `BlueprintValidator` 负责跨字段和可执行性规则；
- API 层不包含 Prompt 和业务校验细节。

## 6. 业务规则校验

除 Schema 外，蓝图必须满足：

1. 角色和状态 ID 全局唯一；
2. 所有引用的角色、状态均存在；
3. 集数与用户选择一致且编号连续；
4. 每集两个选择的意图和后果不能完全相同；
5. 非终集必须有悬念，终集必须能进入结局；
6. 每个选择至少产生一个非零状态变化；
7. 单次状态变化不能超过约定上限；
8. 每个结局条件在理论状态范围内可达；
9. 必须存在高值、低值和中间/混合路径，避免三个同质结局；
10. 不允许要求后续未定义的新角色或关键道具才能完结。

## 7. 错误处理与可观测性

第一次输出失败后，将结构化校验错误反馈给模型进行修复，最多重试两次。三次都失败时返回明确的规划失败错误，禁止保存残缺蓝图。

每次调用记录：

- request ID；
- 模型名称；
- 调用次数；
- 耗时；
- 输入和输出 Token；
- 失败阶段；
- 经过脱敏的校验错误。

日志不得包含 API Key。用户完整灵感默认不写入错误日志。

## 8. 测试与评测

### 单元测试

- 合法的 3 集和 5 集蓝图；
- 错误集数、角色数量、状态数量和数值范围；
- 重复 ID、无效引用和相同选择；
- 不可达结局、终集不收束和非终集无悬念；
- 模型超时、无效 JSON、连续三次失败。

### 固定 20 题材评测

覆盖直播、游戏、悬疑、职场、家庭、情感、校园、科幻等题材。每个样例保存原始结果、校验结果和人工评分，避免只展示成功案例。

合格标准：结构通过，故事具备开端、冲突、反转和结局；两个状态与主题相关；选择能产生不同后果；结局可达且不明显同质化。

## 9. 学习与面试验收

M1 不能只以代码完成为准。负责人还必须：

- 能解释 Pydantic 校验与业务校验的区别；
- 能画出灵感到蓝图的数据流；
- 能独立新增一条业务规则及对应测试；
- 能解释为什么不让 LLM 直接修改故事状态；
- 能回答结构化输出失败、超时、重试和成本控制问题。

## 10. 暂不实现

- 蓝图持久化和数据库迁移；
- 单集正文生成；
- 玩家选择执行；
- 前端页面；
- RAG、长期记忆和多智能体；
- 社区、登录、支付和分享。
